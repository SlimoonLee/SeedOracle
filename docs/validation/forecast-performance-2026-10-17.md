# 地图预测性能排查与修复（0.1.40，2026-10-17）

## 基线与测量范围

- 原版0.111.0，Random Foreseer0.13.19，Combat Solver0.50.1。
- 用户游戏启动日志已确认载入本地0.1.39，先前的动画修复已经生效。
- 在复制的游戏和资料目录运行原生Godot/.NET自检，种子`ROUTE_PERF_20261014`。真实跑局与资料不参与模拟修改。
- 压力场景为含羽翼之靴3次使用机会的密集地图，目标前有5层休息点，保留512条路线。它用于测复杂分支，不能代表所有正常节点。
- 临时测量只在Debug自检主动开启，按阶段记录主线程耗时与分配；Release不保留测量历史。阶段之间有包含关系，不能相加。

## 已确认的问题与改动

1. 旧实现每个候选分支入队前，恢复完整跑局、追加一个坐标、再重新复制完整跑局；时间预算内根本不会处理到的候选也付出了两次复制成本。现在待处理项保存离开节点的坐标，实际出队后只恢复一次，再调用同一个原版`AddVisitedMapCoord`。房间解析前已经应用坐标，分支状态和原版回调顺序保持一致。
2. 状态复制创建整份JSON对象树，遍历地图后再反序列化。现在直接使用原版类型信息经UTF-8深复制，随后从来源恢复地图`CanBeModified`标记。原版会省略false而初始化为true，此特殊处理仍覆盖普通节点、起点及两个Boss节点。没有共享可变玩家、牌组或历史对象。
3. 缓存满12项会全部清空。现在保留最多64项，命中更新访问顺序，只淘汰最久未使用的一项。仍对完整状态、事件页、语言及跑局对象变化失效。
4. 鼠标划过每个节点都会立即同步预测。现在未缓存的远处节点等待80毫秒，只保留最新请求；离开、关闭地图或禁用预测后取消，拖动期间推迟。相邻节点及通过完整状态校验的缓存结果立即显示。由地图原有帧回调检查一个待处理项，没有后台任务或独立计时器。
5. 状态指纹直接生成UTF-8字节再哈希，去掉JSON字符串及二次编码。没有削减指纹字段，也没有按帧复用未经校验的指纹。

## 同场景实测

| 指标 | 改前 | 改后 |
| --- | ---: | ---: |
| 复杂节点首次预测 | 175.72ms | 129.89ms |
| 首次预测主线程分配 | 111,414,912字节 | 103,490,200字节 |
| 状态复制阶段 | 230次 / 106.68ms | 212次 / 66.60ms |
| 连续16次缓存查询 | 1.94ms | 2.42ms |
| 连续16次缓存查询分配 | 2,363,944字节 | 1,241,128字节 |
| 看过另外12个节点后首项仍命中 | 否 | 是 |

首次预测约减少26%耗时、7%分配。分支有时间和工作量预算，优化后可能在预算内计算更多内容；不能把总体分配比率视为每次复制的比率。缓存查询都很短，2ms附近的波动不作为加速依据。

同一份快照各执行32次复制的固定工作比较：旧路径13.08ms、9,580,072字节，新路径5.18ms、7,769,128字节，分配约减少19%。旧路径仅作为Debug测试参照保留。

请求调度测试模拟每16毫秒经过一个节点，共20个节点：经过期间0次计算，最后停留后只取出1次请求；离开后的取消请求0次计算。此项验证请求逻辑，尚未通过用户实际鼠标操作测量帧时间。

## 验证结果

- Debug构建0警告、0错误，隔离完整自检退出码0。
- 完整快照内容对照旧复制路径一致；普通节点true/false、起点与两个Boss的false标记保留，修改副本的牌组、子节点和历史不影响原始快照。
- 羽翼之靴路线55个精确用例通过；66个目标共24,212条路径的枚举约18ms；隐藏面板20次奖励刷新没有收集目标或启动worker。
- 新缓存穿越12节点后仍命中，拿牌与消耗羽翼之靴次数后重新生成；原版库存对照仍匹配。
- 原版商店12例、普通选牌128例、重掷26例及跨组领取3例、商店购买与补货、涅奥到后续商店/奖励/宝箱分支均通过。
- 事件审计106支持、15降级、0不确定、0失败，规划模拟3次成功，真实玩家状态与资料校验不变。
- 锻造分支仍为0预览动画、0误生成的动画节点；Shift滚轮与地图拖动锁定检查通过。
