# 0.1.59 极速商店多购买机制核实（六选三 / 追加购买 / 顺序无关性）

> 本文回答两件事：一、哪些购买项会动哪些随机数流、动多少（逐条目）；二、为什么"先买了哪几件"（集合）而不是"按什么顺序买"（序列）决定每件货物的内容——以及唯一的例外。0.1.54–0.1.58 的单件预测结论（`.local/rng-audit-0113/full/` 反编译 + `blitz-stream` 实测）是本文的基础。

## 证据来源

游戏 0.113.0 反编译（`.local/rng-audit-0113/full/MegaCrit.Sts2.Core.Entities.Merchant/`），叠加 0.1.58 `blitz-stream` 自检的逐条目流计数器差分（每次一条目在影子克隆上真买一次，前后量 `Shops` / `Rewards` / `Transformations` 计数器）。两路证据互相咬合：源码给出"为什么"，实测给出"多少"。

## 1. 货架与预算

`MerchantInventory.GetBlitzEntries`（`MerchantInventory.decompiled.cs:209-236`）：

- 5 件非诅咒条目：14 类（`CardUpgrade..Relic`）中**不重复**加权抽取（`WeightedNextItem`），稀有 3 类（棱镜/稀有卡牌奖励/升级稀有卡）权重 0.5，其余 1.0。
- 1 件诅咒条目：6 类（`Glam..FullHealAndMaxHp`）均匀抽取。
- **构造期**就消耗 `Shops` 的两类：`CardEnchant`（掷附魔 +1）、`PrismaticCardReward`（掷角色 +1）。这发生在生成货架时，与购买顺序无关。
- 预算 `BlitzChoicesRemaining = 3`（`Setup`，`:152-155`）；每次**成功**购买 -1（`UpdateEntries`，`:265-285`），降到 0 时全场 `Available → Disabled`。
- 取消选牌 = 购买失败：条目保持 `Available`，次数不减，流不动。

`TwoMoreChoices`（`BlitzMerchantTwoMoreChoicesEntry.cs`）：`OnTrySelect` 先 `GiveCurse()`（`Shops` +1）再 `BlitzChoicesRemaining += 2`。买它本身耗 1 次，净 +1 次可带走。**追加购买只此一处**；它必须趁次数未用完时买（次数到 0 后全场禁用）。

## 2. 逐条目的流消耗（购买时）

诅咒条目全部先 `GiveCurse()`（`BlitzMerchantEntry.GiveCurse`：`Shops.NextItem` 从诅咒池抽 1 张进牌库）。数字为 0.1.58 `blitz-stream` 实测，与源码结构一致：

| 条目 | Shops | 其他流 | 需你选牌 |
|---|---|---|---|
| 卡牌奖励 / 升级卡牌奖励 | +18（2 屏 × 9） | – | 否 |
| 附魔卡牌奖励 | +12（1 屏 + 附魔掷） | – | 否 |
| 稀有卡牌奖励 / 棱镜 / 无色 | +9（1 屏） | – | 否 |
| 升级稀有卡牌奖励（诅咒） | +10（诅咒 +1 + 屏 9） | – | 否 |
| 各稀有度卡牌奖励（诅咒） | +1（诅咒） | **Rewards +9**（3 屏走 `ForNonCombatWithUniformOdds` 默认流） | 否 |
| 药水 ×2 | +4 | –（+1 药水位不是 RNG） | 否 |
| 遗物 | +1（稀有度） | 共享遗物袋出队 1 件（无 RNG） | 否 |
| 双遗物（诅咒） | +3（诅咒 + 2 稀有度） | 遗物袋出队 2 件 | 否 |
| 多加 2 次（诅咒） | +1（诅咒） | – | 否 |
| 满血 + 最大生命（诅咒） | +1（诅咒） | – | 否 |
| 升级 / 删牌 / 附魔 | **0** | – | 是 |
| 变化 | 0（抽取走 Transformations） | Transformations 1 次 | 是 |
| 格拉姆附魔（诅咒） | +1（诅咒，**选牌之后**掷） | – | 是 |
| 自动升级 ×2 | ≈ 牌库张数（`StableShuffle` 整库洗牌） | – | 否 |

要点：

- "看起来固定"的条目几乎都会掷：满血/多加 2 次各藏一张诅咒，遗物要掷稀有度；诅咒身份随位置变。
- 流消耗量只依赖**条目类型**（外加自动升级依赖当时牌库张数），不依赖购买时刻的其他状态。
- 遗物袋是队列不是骰子：`PullNextRelicFromBack` 按袋尾出队，取哪件由袋序决定，稀有度才走 `Shops`。

## 3. 顺序无关性（本窗口设计的基石）

**命题**：某件货物 X 的内容，只取决于"在它之前已完成购买的货物**集合** S"，与 S 内部的先后顺序无关。

论证（逐项核对 X 的输入）：

1. **X 读到的流位置** = 基准 + Σ_{s∈S} delta(s)。delta 是每类固定值，求和与顺序无关。
2. **Rewards / Transformations**：全货架只有 `CardRewardOfEachRarity` 动 Rewards（每架至多 1 件诅咒条目，类型不重复），只有变化动 Transformations。S 内不存在同类竞争者。
3. **遗物袋**：出队按袋尾计数，S 里 k 次遗物购买永远拿走同一批 k 件；X 自己的稀有度掷在 X 的位置上。谁先拿不影响 X 拿到袋里第 k+1 件。
4. **诅咒池**：X 的诅咒在 X 自己的位置掷，与 S 顺序无关。
5. **牌库状态**：S 里各件赠予的牌/诅咒是"每件在自己的位置上读出来"的，逐件内容由该件的位置决定（同样只依赖它的前缀集合）。牌库**多重集**是 S 的函数；牌库**顺序**不是（后买的牌后进库）。见第 4 节例外。

**例外：自动升级（RandomUpgrades）**。`StableShuffle(Shops)` 洗的是**当时牌库的顺序**，取前 2 张升级。若 S 里有赠牌条目且玩家实际领奖，进库顺序随购买顺序变，洗牌结果可能不同。窗口对这类行标注"结果按常见顺序推算，前序奖励实际选牌会改变牌库顺序"；流推进量（洗牌消耗 ≈ 牌库张数）同样按当时的多重集推算。

**关于"变化"的常见疑问（为什么结果这么少）**：变化读的是 **Transformations 流**，与购买消耗的 Shops 流完全独立——整个商店流程里只有一次**已完成的**变化才把它推 +1。因此先买多少卡牌奖励都不改变变化读取的位置；且游戏对每个候选都在**同一位置**调 `rng.NextItem(池子)`，同池候选几乎全部落到同一张结果（只差"抽中自己被排除"造成的相邻错位）。结果多样只来自三个源头：相邻错位、候选属于不同池子（无色 / 诅咒 / 棱镜角色池）、诅咒源不受稀有度过滤（整个诅咒池）。实测：买"多加2次选择"把愧疚送进变化 → 铃铛的诅咒；角色池牌库牌与奖励牌 → 同一张双重打击。

**推论**：完整组合空间 = 每件在场货物 × 其余货物的有效前缀子集（预算约束：|S| + 1 ≤ 剩余次数 + 2·[S 含多加 2 次]），最坏 6 × 32 = 192 行，相同结果合并后远少于此。**不需要**枚举 3!~5! 的购买序列。

## 4. 建模边界（与 0.1.54 以来的原则一致）

- **前序购买按"已完成、奖励界面未领取"建模**：探针 `GenerateWithoutOffering()` 让牌/遗物/药水掷出来但不领取。只有读取牌库的"自动升级"受实际领奖影响（见上）。
- **需选牌的前序条目按"自动选第一个候选完成"补全**（升级/删牌/附魔/变化/格拉姆）：这些条目对后续货物的影响只在流位置（格拉姆的诅咒 +1、变化的 Transformations），选哪张牌不改变流的推进；此假设写进窗口脚注。
- **每件货物自身的展示保持选牌感知**：需要你选牌的条目仍列候选与逐候选结果（0.1.57 的变化表），不代选。

## 5. 与既有实现的关系

- 店内浮窗（0.1.55–0.1.58）回答"悬浮的这一件 + 单件先行"，保持不变；本窗口把"任意前缀组合"与"整包购买顺序规划"补全。
- 地图/路线规划侧仍按"这一项先买"推算并保留脚注（0.1.53 边界：极速商店进店后逐项选择，规划不代选）。
- 自检：`blitz-plan`（全景枚举与合并）、`blitz-plan-order`（顺序无关性实测：A→B→X 与 B→A→X 逐字相同）、`blitz-plan-seq`（查表 vs 逐步真买 A/B）。
