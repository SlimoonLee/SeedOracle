# 0.1.30 复杂路线性能修复

## 原因与修复

`NMapScreen.Open` 会调用战损面板的 `Configure`。此前面板收起时也逐节点搜索路线、克隆跑局并生成候选；持有羽翼之靴时，这项预处理会放大奖励结算后打开地图的停顿。现在收起时只绑定地图，用户展开时才生成列表；用完整跑局指纹复用列表，领取卡牌、遗物、用药、RNG、地图或羽翼之靴次数变化都会在再次展开时使缓存失效。候选缓存不依赖 Combat Solver 是否可用。

旧路线搜索用广度优先队列复制每个路线前缀，还会展开已经超过目标楼层的分支。现在预先计算到达目标最少需要的自由移动次数，剪去不可达分支；深度优先推进到目标，只有完整路线才生成路径数组。各条有效路线仍分别保留，512条路线与8192状态的上限保持不变，未枚举完整时仍标记截断。

战斗候选只搜索战斗或问号目标，提前排除必须经过另一场战斗或未决先古的线路；问号在独立跑局中按原版赔率/RNG解析，如果途中变成战斗或事件，就停止该候选的推演。

## 本地测量

相同种子 `ROUTE_PERF_20261014`、相同66个未来节点、羽翼之靴剩余3次，均使用复制资料的无头游戏。分配量是本线程累计分配字节，并非常驻内存。

| 项目 | 修复前 | 修复后 |
| --- | --- | --- |
| 全图路线搜索 | 1079 ms | 17 ms |
| 搜索累计分配 | 682839232 B | 15230824 B |
| 返回完整路线 | 5780 | 24212 |
| 被截断的目标 | 66 | 41 |
| 全图战斗候选预处理 | 3724 ms | 1 ms |
| 候选预处理累计分配 | 3467745024 B | 191384 B |

上表候选测量位于开局先古尚未选择的阶段，两版都返回0个可计算目标；不能据此承诺任意后续场景均为1 ms。修复前基线测量完成，但额外开销使 AutoSlay 后续启动超时，因此该次仅作为性能基线。修复后的整套审计退出码为0。

## 验证

- 55个精确对照：0至3次羽翼之靴及无限飞行，逐完整路径比较坐标、是否消耗次数、自由移动是否可用；下一场战斗筛选与未经优化的全路径推演相同。
- 高分支测试能在预算内取得512条通往目标的完整路线，并正确标记截断。
- 连续20次收起面板刷新：候选生成次数0。领取卡牌和消耗一次羽翼之靴后仍不在收起时计算，再展开会更新列表；相同状态再次展开复用缓存，无自动 worker。
- 原版商店12例、有序重掷26例、前置选择、变牌摘要、药水、事件后续页和规划模拟通过；事件审计111支持、10降级、0不确定、0失败。
- 跑局和资料纯度检查通过。实际游戏画面与主游戏帧时间未测量。

原始基线保存在 `.local/route-performance-20261014/baseline-report.txt` 和 `baseline-godot.log`；修复后报告为同目录的 `smoke-report.txt`、`godot.log`。
